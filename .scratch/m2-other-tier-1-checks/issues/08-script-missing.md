# 08: `script/missing` — a command whose script does not exist

**What to build:** the check that reads `npm run X` and its siblings as a claim about a manifest, and says when that manifest has no such script.

**Blocked by:** `04` (ignores)

**Status:** done

`docs/spec/SPEC.md` § 3 specifies it in four lines: detect `npm run X`, `pnpm run X`, `pnpm X`, `yarn X`, `bun run X`, `deno task X`, `make X` in code blocks and in inline code; verify against `package.json#scripts` (the nearest one in the tree, for monorepos), `Makefile` or `deno.json#tasks`; suggest a script at edit distance ≤ 2 and make it autofixable.

Three of those lines are arithmetic. The first one is a **command-line parser**, and it is where every false positive of this check will come from.

## The claim is a command, not a word

`path/missing` claims a fragment of inline code. This check cannot: `pnpm build` is a claim about `build`, and `pnpm add zod` is a claim about nothing. So the extractor has to answer three questions in order, and any of them saying "I do not know" means no claim:

- [x] **Which manager**, from the first word of the command. Anything else is not ours.
- [x] **Is this a script invocation at all.** `pnpm run X` says so in the syntax. `pnpm X` does not. ~~A per-manager builtin list settles it, and it is the only place in this ticket where being one release behind can produce a finding — so the list errs long.~~ **Withdrawn after the first corpus run, see the comments:** the list was the wrong instrument, because `pnpm vitest` is not a subcommand — it is a binary. The bare form is not read at all ([ADR-0012](../../../docs/adr/0012-a-bare-pnpm-x-is-not-a-script-claim.md)), `make` excepted.
- [x] **Which token is the script name**, once the flags are out of the way. `pnpm -r build`, `npm run build --workspace=api`, `make -C docs html` all name a script *somewhere else*, in a package we cannot identify from here: those are dropped whole rather than resolved against the wrong manifest.

A line is split on `&&`, `;`, `|` first, so `pnpm build && pnpm test` is two claims, and leading `VAR=1` assignments and a `$` prompt are stripped.

- [x] The claim's `text` is the **command segment**, which is what `SPEC.md` § 5's sample output shows (`pnpm run test:e2e`), and `offset` covers exactly it. `meta` carries the runner, the script and where the name sits inside the text, so `--fix` can replace one token in M3 without re-parsing.

## Where it reads from

- [x] **Inline code**, with the same two prose gates the path claims pass (`externalRootSections`, `proseDisclaims`).
- [x] **Code fences**, which `path/missing` deliberately does not read — `ARCHITECTURE.md` § "Markdown parsing" assigns fences to the script and command claims, and a command block is the normal way a context file tells an agent how to build the project. A fence declaring a non-shell language is skipped, and so is a `#` comment line inside one.

## ~~`test` and `start` are given up on purpose~~

**Moot as written.** The section argued for excluding two lifecycle aliases from a bare form that no longer exists: `pnpm test` and `npm start` are dropped now because *every* bare invocation of the npm family is. `pnpm run test` is still claimed, for the reason the last sentence gave — the explicit keyword removes the ambiguity — and that sentence is the only part of this section that survived.

## The manifest question, and ADR-0005 answers it

The nearest manifest is what SPEC asks for and what the message names. It is **not** the only place the script is looked for.

[ADR-0005](../../docs/adr/0005-a-path-that-exists-somewhere-is-not-drift.md) already decided this shape for paths: something that exists somewhere in the repo is not drift, and the loss — a thing that moved between packages goes undetected — is accepted. A monorepo's context file written from the root (`pnpm test` in `packages/api/CLAUDE.md`, with the script defined at the root) is the same situation, it is common, and reporting it is exactly the false positive that gets a tool uninstalled.

- [x] Report only when **no manifest of that runner's kind** in the repo has the script. The nearest one is still what the message names, because it is the one the reader will open.
- [x] **No manifest at all means silence.** No `package.json` anywhere, no `Makefile`, no `deno.json`: there is nothing to verify against, and the same rule `link/broken` follows for a target that does not exist. A `make build` in a repo whose Makefile is generated by `./configure` is not ours to report.

## A Makefile we cannot enumerate is a Makefile we say nothing about

`package.json#scripts` and `deno.json#tasks` are objects: their keys are the whole truth. A Makefile is a program.

- [x] An `include` line means targets live in a file we did not read.
- [x] A pattern rule (`%.o: %.c`) or a computed target name (`$(BINS):`) means the set of valid targets is not the set of literal names.

In any of those cases the file is marked non-enumerable and every claim against it is dropped. `.PHONY:`'s prerequisites *are* target names and get added; special targets (anything starting with `.`) are not targets a reader invokes.

- [x] `deno task` also runs `package.json` scripts, so its lookup is the union of both. A `deno.jsonc` that does not parse as JSON is non-enumerable, not empty.

## The suggestion, and the second autofix in the project

`SPEC.md` § 8: a single script at edit distance ≤ 2. That is `nearestUnique` in `src/fix/suggest.ts`, already capped at 2 and already refusing to choose between two candidates.

- [x] The suggestion's `value` is the **whole corrected command**, because that is what `offset` covers and `--fix` replaces. `pnpm run test:e2e` → `pnpm run test:e2e-ci`.
- [x] `fixable: true` with `confidence: 1`. It is unambiguous by construction: one candidate, within two edits, in the manifest the command already resolves to.
- [x] `test/corpus-bookkeeping.test.ts` asserts `fixable: 0` over the corpus. If a real repo has a near-miss script, that assertion becomes what ADR-0006 condition 2 says — zero *false positives* among the fixable findings — and the finding is classified by hand first. Same foreseen change ticket `07` recorded.

## Where the pieces go

- `src/extract/scripts.ts` — the command parser and the claims. Already named in `ARCHITECTURE.md`'s tree.
- `src/verify/manifest.ts` — also already named there: what tasks each directory offers, per runner, and the nearest one walking up. Built once per run, before verification, like `anchor-index.ts` and for the same reason: `Check.run` is synchronous and the budget in SPEC § 9 dies if a check reads from disk.
- `src/verify/checks/script-missing.ts` plus its entry in `CHECKS`.
- `CheckContext` grows a `tasks` field. The M2 spec expected this growth in ticket `01`; it did not happen there, and it happens here rather than being pre-empted for checks that do not exist.

## Tests

- [x] Fixture `scripts`: one broken script per runner, the near-miss with its fix, and a monorepo shape where the nearest `package.json` is not the root's.
- [x] Negative cases in the same fixture, one per refusal above: `pnpm add`, `pnpm test`, `pnpm -F api build`, `make -C docs html`, `npm run <script>`, a script defined at the root and named from a package, a repo with no manifest, a Makefile with an `include`, a fence declaring `python`.
- [x] Unit tests for the command parser and for the Makefile target reader. Both are "wrong in a way a fixture would not localise" (`ARCHITECTURE.md` § Testing).

## Corpus

Owed before and after (ADR-0007). This check reads **code fences**, which no check has read before, so its new surface is not the frontmatter blocks the last three tickets moved over — it is every command block in 177 sources. Expect movement, classify each finding by hand in `CLASSIFICATION.md`, and re-check the nine ADR-0006 conditions aggregate.

If a validation repo produces a false positive, the responses in order are: narrow the rule on principle and write down what it gave up, or withdraw the rule. Widening a builtin list because one repo tripped over it burns that repo under condition 9.

## Out of scope

- `command/unknown` (tier 2, M5): whether the *binary* exists is a different check with a different list. This one only reads managers it knows.
- `dep/missing` and everything else about the manifest's dependency sections.
- Cross-package resolution: `pnpm --filter api build` is dropped, not resolved. Identifying the package a filter names means reading the workspace globs, and the finding it would buy is one nobody has asked for.
- `--fix` itself (M3). This ticket only sets the flag.

## Comments

Closed 2026-09-10. 20 new tests, 375 in the suite. Corpus run in full, twice: **49 repos, 177 sources, 16 → 17 findings, one snapshot changed.**

It also produced [ADR-0012](../../../docs/adr/0012-a-bare-pnpm-x-is-not-a-script-claim.md).

### The corpus rejected half the check on its first run

Nine findings, **eight false**, and the review is the whole story of this ticket ([CLASSIFICATION.md § Twelfth round](../../../test/corpus/CLASSIFICATION.md)). Three root causes, three fixes, all in calibration repos so nothing was burned under condition 9:

- **The bare `pnpm X` form had to go.** `pnpm vitese`-shaped mistakes are not what the form produces in practice; `pnpm vitest run x`, `pnpm prettier --write x`, `pnpm wrangler types` and `yarn biome check` are, and every one of them runs a **binary** from `node_modules/.bin`. Three were `fixable`, which is the one class ADR-0006 condition 2 admits none of: the tool offered to rewrite `pnpm vitest run <path>` into `pnpm test run <path>`. The ticket had planned for this form with a curated subcommand list, which was the wrong instrument — `vitest` is not a subcommand. `SPEC.md` § 3 was corrected, ~100 lines of subcommand lists were deleted, and ADR-0012 records what the narrowing gives up.
- **A trailing `#` comment was part of the claim.** It landed in `Claim.text` and would have landed in whatever `--fix` wrote back.
- **A code block can be a table.** `spatie/bloom` documents its `Makefile` as a two-column index, and read as a command its first line invokes a target called `list`. Two spaces in a row are now a column, not an argument.

None of the three could have come from a fixture: we wrote the fixtures, and `pnpm vitest` is not a shape anybody invents while testing their own parser.

### The one true positive

`tursodatabase/turso` `.claude/skills/mvcc/SKILL.md:91` says `make test-mvcc`. The `Makefile` has forty targets, no `include`, and no `test-mvcc`. Nothing is within two edits of it, so the finding carries no suggestion — which is why `fixable: 0` still holds across the corpus.

### What the quiet is worth

93 script claims over 177 real sources: 84 resolved against a manifest, 8 dropped for having no manifest of that runner's kind, 1 reported. `make` contributed 45 of the 93, `npm` 32, `pnpm` 11, `bun` 5. **`yarn` and `deno` contributed none**, so the deno half of the check and `yarn run` are fixture-only evidence, and ADR-0012 records `yarn run`'s residual risk — it accepts a binary where `pnpm run` does not.

### Two things the ticket got wrong before the corpus did

- The bare form was planned with a subcommand list and the lifecycle aliases excluded "on purpose". Both are now moot, and the ticket's section on them reads as a rule that never shipped. It is left standing because ADR-0012 is what replaced it and the reasoning is worth the contrast.
- `CheckContext` grew a `tasks` field here rather than in ticket `01`, where the M2 spec expected it. Pre-empting the growth for checks that did not exist would have shipped a field nobody read; the spec's expectation was the thing that was wrong.

### The docs are audited by the tool, and they moved

`README.md` still said "one check, `path/missing`" three tickets after that stopped being true — a stale document in the repo of a tool that exists to find stale documents. It now lists the five, and the M2 status line says the milestone is complete.

The second invocation (`--config driftwatch.docs.config.ts`) caught two of our own documents claiming commands: `SPEC.md` § 3's own `npm run X` specification line, which produced six findings and is what the metavariable rule was written for, and the README's example commands, which were reworded rather than ignored.

### What the code review changed

Both axes found something real, and one of them found the same class of bug the corpus had already caught once.

- **A flag after the name was not read.** The rule was "a flag before the name drops the segment", and `npm run buildd -w api` therefore reached the check — where it would be answered from the nearest manifest, with a `fixable` suggestion drawn from **another package's** script list. Same class as the `pnpm vitest` findings, arrived at from the other direction. The rule is now "a flag that moves the question elsewhere, wherever it sits": `--filter`, `--workspace`/`-w`, `-r`, `--prefix`, `-C`, `--if-present`, with the `=` form matched too.
- **The suggestion pool ignored the runner's own lookup union.** Existence was answered over `deno.json` *and* `package.json`, but the candidates came from the first file only, so a `deno task` near-miss of a package script was reported without the suggestion naming it. `nearestTaskFiles` now returns one file per kind and the check pools them.
- **`bun run X` shares Yarn's residual risk** — both fall back to `node_modules/.bin`, `npm run` and `pnpm run` do not. ADR-0012 said this of Yarn only; it now says it of both, with why they are kept and what to do if one fires.
- **Four narrowings existed only in the code**: `--if-present`, the metavariable rule, the concept words (`script`, `task`, `target`), and the column layout. `SPEC.md` § 3 now states them, because "the specification is primary source" cuts both ways — a rule that only the code knows is a rule the next reader will delete.
- **`npm run-script` was in the code and not in SPEC § 3.** Added.
- **Six tables keyed on the same domain concept** became two records: one `ManagerGrammar` per manager (runner, keywords, bare) and one `RunnerFacts` per runner (filenames, lookup, noun). Adding a manager is one entry, and the facts about it cannot fall out of step.
- **`ScriptFact.at` is `nameOffset`**, since three different offsets in the module were called `at`. `suggestScript` takes the fact rather than two of its fields, and derives `fixable` from `FIXABLE_THRESHOLD` instead of hardcoding `true` next to it. `splitCommands` takes the separator width from the match rather than reconstructing it.
- **The message names the manifest by path**, not by basename: `script not in packages/api/package.json` says which of the four the reader has to open, and at the root the two read the same.
- **`ARCHITECTURE.md` was stale in two places** the diff had already edited around: the tree said `manifest.ts` reads `pyproject`/`go.mod`/`Cargo`, and § Extensibility promised a `ctx` with fields that do not exist. Both now describe what is there.
- **The fixture only fired for three of the six managers.** `yarn run`, `npm run-script` and `bun run` now have positive cases, which matters most for `yarn` — ADR-0012 names it as the form with no out-of-sample evidence at all.

Corpus re-run after all of it: **unchanged, 17 findings.** Nothing above was a precision change; the flag rule can only remove claims, and no corpus command carried one.

### The ADR needed the escape hatch to describe the risk it records

The sentence in ADR-0012 explaining why `bun run` is kept uses `bun run vitest` as its example, and the second invocation reported it — as `fixable`, offering to correct it to `bun run test`. The document about the residual risk trips over the residual risk.

It carries a `<!-- driftwatch-ignore-next-line script/missing -->` and says so in the text. That is the directive from ticket `04` doing the job it exists for: a document naming a command it does not run. The README's example line was reworded instead, because a bullet list of five checks is not the place to explain a comment nobody can see rendered.

**Left undone, deliberately:** the two prose gates (`externalRootSections` plus `proseDisclaims`) are now copied in three extractors and recomputed once per extractor per source. Hoisting them onto `ExtractContext` is the right shape and touches `paths.ts`, `links.ts` and `run.ts` — three modules this ticket has no other reason to open. It belongs to the next ticket that touches extraction, not to this one.
