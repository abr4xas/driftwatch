# 01: Implement `ignore`

**What to do:** land the `ignore` config key described in [`spec.md`](../spec.md).

**Type:** task

**Blocked by:** nothing.

**Status: resolved 2026-09-24.** Landed, verified, and the corpus moved nothing. See §"Done".

## The change

- `src/core/config.ts`: `ignore?: readonly string[]` back in `Config`, in `KNOWN_KEYS`, and
  validated by `stringArray` like `sources`.
- `src/core/discover.ts`: after discovery and after `sources` resolution, drop every source
  whose repo-relative path matches an `ignore` glob. `tinyglobby` is already a dependency and
  `sources` already matches globs against the repo index — this is the same matching, used to
  subtract.
- `src/cli/init.ts`: `--init` writes the key commented out, with the one-line reason. It writes
  `sources` and `checks` the same way; a key nobody can discover is a key nobody uses.
- Regenerate `CONTRACT.md` with `pnpm surface`. The frozen surface grows by exactly one config
  key and nothing else — that diff is the acceptance check.

## Documentation, and the two places that currently say the opposite

- `docs/spec/SPEC.md` § 7 says three keys "were withdrawn in `1.0.0`" and are "refused like any
  other unknown key". That paragraph has to say which one came back and why, in the same voice:
  it was withdrawn for being unimplemented, not for being wrong.
- `docs/guide/usage.md` gains `ignore` in the config table, next to the inline directives, with
  the distinction spelled out: **directives for a document you own, `ignore` for one you do
  not.**

## Tests

- The four rules in `spec.md` § "The rules it has to obey", one case each. The one that will
  break first if the implementation is careless is rule 2: an ignored path that discovery found
  on its own, never named in `sources`.
- A glob matching nothing exits 0 and audits everything else — the deliberate asymmetry with
  `sources`, which errors.
- `--init` output mentions the key, and the config it writes still loads.
- A repo-root-relative match, so that `'skills/**'` does not accidentally match
  `packages/a/skills/foo.md` through a substring.

## Verification

`pnpm typecheck && pnpm test && pnpm build && node ./dist/cli.js --help`, and `pnpm corpus
--check` before and after — not because this touches a heuristic, but because it touches
discovery, and a source that stops being audited is a snapshot that changes. **It must change
none**: this repository's own `driftwatch.config.yaml` sets no `ignore`, so a moved snapshot
means the key is subtracting something it was not asked to.

## Not in this ticket

Deciding whether driftwatch should ignore anything by default. It should not, and nothing here
proposes a default: an empty `ignore` is the shipped behaviour and the key is opt-in.

## Done

The key is in, and every rule `spec.md` fixed has a test naming it.

- `src/core/config.ts` — `ignore?: readonly string[]`, in `KNOWN_KEYS` between `checks` and
  `skillRoots`, validated by the same `stringArray` as `sources`.
- `src/core/discover.ts` — `withoutIgnored` runs **after** discovery and after `sources`, over
  the merged list. It uses the `ignore` package, the same matcher `matchConfiguredSources`
  already uses, so both keys read one syntax: gitignore patterns from the repo root.
- `src/run.ts` — carried through like `skillRoots`, absent when the config does not set it.
- `src/cli/init.ts` — written as a live empty key, with the directive named beside it so a
  reader meets the distinction where they meet the config.

### The asymmetry, and it is deliberate

`sources` throws on a pattern matching nothing; `ignore` does not. A source you asked for and
did not get is a hole in the audit and has to be loud. An `ignore` for a `third_party/` this
repository does not have is a config that still works, and failing on it would punish sharing
one config across repositories.

### Verified

```
pnpm typecheck && pnpm lint && pnpm test && pnpm build && node ./dist/cli.js --help
885 tests, 0 lint errors

pnpm corpus --check   96 repos · 1901 sources · 337 findings   identical to the baseline
```

**No snapshot moved**, which is the check that matters here: this repository sets no `ignore`,
so a moved snapshot would mean the key subtracts something nobody asked it to.

`CONTRACT.md` grew by exactly one line — `ignore` under "Config keys" — regenerated by
`pnpm surface`, which is what records the change as deliberate rather than noticed.

### End to end, on a throwaway repo

A `CLAUDE.md` naming a missing file of its own, and a `.claude/skills/vendored/SKILL.md`
naming a missing file of somebody else's:

```
no config                        2 files · 2 problems
ignore: '.claude/skills/vendored/**'   1 file  · 1 problem
ignore: 'third_party/**'         2 files · 2 problems, exit 0
```

The ignored document is **gone**, not skipped — it was never a source — and the repository's
own drift is still reported, which is the whole distinction the key exists to draw.

### Three documents that said the opposite, and now do not

- `SPEC.md` § 7 described three withdrawn keys. It now describes `ignore` with its three rules,
  and says of the withdrawal that `ignore` came back the other way: implemented, which is the
  answer for a key withdrawn for being unimplemented rather than for being wrong.
- `docs/guide/usage.md` gains the key and the sentence that separates it from the directives —
  one for a document you maintain, one for a document you do not.
- The two tests that pinned the withdrawal now pin two keys instead of three, and a new one
  asserts the template names `ignore` and points at the directive.
